fru-lab · Throughput Tester

Throughput Tester 使用指南

Throughput Tester 模擬大量 gNB 和 UE，對任何 5G 核網做 N2 建立、註冊、PDU session，再打固定速率的上下行流量，量 UPF 實際轉送了多少。它不依賴 fru-lab 部署的 free5GC。這份指南涵蓋啟動、部署架構、Setup 頁每個欄位的意思與調整方向，以及怎麼讀結果。

它做什麼

引擎是獨立的程式 fru-tester。fru-lab 保存你的設定檔，並把 Tester 各頁的 API 轉給 fru-tester（用共用的 API token）。一次 run 依序做這些事，每一段都有即時統計：

N2 建立每個 gNB 開一條 SCTP、送 NG Setup
註冊gNB 一 up，它的 UE 就開始註冊
PDU session每個註冊成功的 UE 建一個
流量PDU 建好 500 ms 後開始打 UL／DL，確認從 UPF 回來
Stop 之後流量立即停 → UE Deregister（核網一併釋放 PDU）→ 關 SCTP → 移除 IP 與路由
  • UE 不開無線連線：每個 gNB 透過自己唯一的 SCTP association，直接在 NGAP 裡帶它所有 UE 的 NAS 訊息。
  • 沒有 TUN 介面：UL 由 tester 直接組成 GTP-U 封包送給 UPF；DL 由 tester 送一般 UDP 給 UE IP，經路由進 UPF，UPF 封裝後送回 gNB 的 N3 IP。
  • 每個封包都帶一個小標頭（UE、序號、送出時間），UPF 做了 NAT 也認得出是哪個 UE；上一次 run 殘留的封包會被忽略。
  • 流量一直跑到按 Stop 或達到最長執行時間。收尾中再按一次 Stop（Skip cleanup）會略過剩下的 Deregistration，但 SCTP 一樣關、IP 一樣清。收尾結束才能開始下一個 run。

開始之前

  • SCTP 模組：跑 fru-tester 的主機要先 sudo modprobe sctp（要開機自動載入：echo sctp | sudo tee /etc/modules-load.d/sctp.conf）。
  • 權限：fru-tester 用 root 或 CAP_NET_ADMIN 執行。run 開始時它會在網卡上加每個 gNB 的 IP、加 UE pool 的路由，結束時移除。
  • IP 規劃：挑一段沒人用的 CIDR 和起始 IP。fru-tester 會跳過網路與廣播位址、AMF 與 UPF 的 IP、以及這台主機上已經有的 IP。它看不到別台機器、Docker bridge 上的容器、k8s pod 用掉的 IP（例如 fru-lab 部署的 gNB 容器 10.0.1.2），所以起始 IP 要從遠一點的地方開始，例如 10.0.1.100。
  • 訂閱資料：fru-tester 不會建訂閱。每個 UE 都要在核網裡有：plan preview 顯示的 SUPI（每個 gNB 一列，列出第一個與最後一個 SUPI）、UE 樣板的 K、OPc、AMF、SQN，以及 gNB 樣板有宣告的切片（S-NSSAI）。fru-lab 的 Subscribers 頁可以一次新增大量 UE（IMSI 逐一加 1），但它管的是 fru-lab 自己部署的核網；別的核網要在那個核網的 webconsole 建。
  • free5GC 的兩個設定：SMF 的 urrThreshold 要調大（fru-lab 的範本是 10 GB），否則高速率時 UPF 每一兩個封包就報一次用量，DL 會斷；CHF 的 cgf.enable 要是 false，否則 PDU session 會卡 10 秒後逾時。fru-lab 的範本已經這樣設，其他核網或舊版要自己改。

啟動 fru-tester

開發模式

make backend frontend tester
make run          # fru-lab，:8888，讀 config.yaml
make run-tester   # fru-tester，127.0.0.1:9100（sudo），讀 tester.yaml

config.yaml 的 backend.tester.url、apiToken 要和 tester.yaml 的 listen、apiToken 一致。backend.tester.url 空白時，Tester 各頁會顯示「Throughput Tester is not configured」。

Docker Compose

docker/docker-compose.yaml 讓 fru-tester 用 host network 執行，權限是 NET_ADMIN（加 gNB IP 和路由）。fru-lab 透過 http://host.docker.internal:9100 連到它。

tester API 會在 host 的所有網卡上聽，所以 docker/tester.yaml 和 docker/config.yaml 的 apiToken 都要改掉預設值。兩個 image 用 make docker 建。

部署架構：同一台還是兩台

tester 和 5GC 同一台 fru-lab 預設

  • 最簡單：fru-lab 部署的 free5GC 在 Docker bridge docker-cn-ran 上，Setup 頁的預設值直接能跑。
  • 封包經 veth 進 UPF 容器後，bridge、gtp5g、NAT 的處理大多在 tester 送出封包的那顆 CPU 上做完，所以 tester 與 UPF 搶同一批 CPU。量到的是「兩者合起來」的上限。
  • 實測：96 CPU 機器，10 gNB × 1000 UE × 30 Mbps，上下行各 30 Gbps，CPU 約 90%。

tester 和 5GC 分兩台 量 UPF 上限時建議

  • A 主機只跑 5GC，B 主機只跑 tester，量到的才是 UPF 自己的上限。
  • tester 那台的發送端幾乎不會是瓶頸（Bench：一條發送線 19–41 Gbps，看 CPU）。
  • 要多注意網路：同一個 L2、同一個 subnet、網卡依 port 分流。步驟見下面。

5GC 在 k8s、N2/N3/N6 用 macvlan 時：主機上看到的 N2/N3/N6 網卡沒有 IP，IP 在 pod 裡。macvlan 的子介面（pod）連不到同一台主機的母網卡，所以 tester 如果也跑在這台，不能直接用那幾張網卡，要先在主機上開 macvlan 子介面給 tester 用（ip link add n3-t link N3 type macvlan mode bridge，N2、N6 同理），Setup 頁的介面填子介面。tester 在另一台、經實體線連過去就沒有這個限制。

兩台機器：B 主機接到 A 主機的 k8s 5GC

例子：A 主機用 k8s 跑 5GC，N2、N3、N6 是綁在實體網卡上的 macvlan；B 主機跑 fru-tester，三個網口用線直接接到 A 的三個網口。先填你 B 主機的值，下面的指令會跟著換。

預設值只是範例。網卡名稱用 ip -br link 查，UE pool 看 SMF 設定（free5GC 是 smfcfg.yaml 的 pools）。下面的 IP 以這組為例：AMF N2 172.22.49.140、UPF N3 172.23.49.140、UPF N6 172.26.49.140，三個網段都是 /16；gNB 從 172.22.6.1、172.23.6.1 開始，sink 是 172.26.6.1/16。

1. 找出 B 的哪張網卡接到哪個網路

每張網卡先暫時加一個 IP、ping 對面的 pod，通了就知道是哪個網路，再拿掉。用 .6.250 這種不會和 gNB 撞到的 IP。

在 B 上
ip -br link   # LOWER_UP 代表線有接上

sudo ip link set ens2f0 up
sudo ip addr add 172.22.6.250/16 dev ens2f0
ping -c 3 -I ens2f0 172.22.49.140
sudo ip addr del 172.22.6.250/16 dev ens2f0

sudo ip link set ens2f1 up
sudo ip addr add 172.23.6.250/16 dev ens2f1
ping -c 3 -I ens2f1 172.23.49.140
sudo ip addr del 172.23.6.250/16 dev ens2f1

sudo ip link set ens2f2 up
sudo ip addr add 172.26.6.250/16 dev ens2f2
ping -c 3 -I ens2f2 172.26.49.140
sudo ip addr del 172.26.6.250/16 dev ens2f2

2. B 主機的準備

在 B 上
sudo modprobe sctp
echo sctp | sudo tee /etc/modules-load.d/sctp.conf

# 三張網卡只要 up，不用加 IP：run 開始時 tester 會用 CIDR 的遮罩加 gNB IP，
# sink 也照 Setup 頁填的遮罩（172.26.6.1/16）加到 N6 網卡上，結束時移除
sudo ip link set ens2f0 up
sudo ip link set ens2f1 up
sudo ip link set ens2f2 up

# UDP 依 port 分流（只有 IP SA / IP DA 時才要改），兩台的 N3、N6 都要
ethtool -n ens2f1 rx-flow-hash udp4
sudo ethtool -N ens2f1 rx-flow-hash udp4 sdfn

Sink IP 要帶遮罩：Setup 頁填 172.26.6.1/16，tester 加到 N6 網卡上時用同一個遮罩，主機才會有到 172.26.0.0/16 的路由，「UE pool 經由 172.26.49.140」這條路由才加得上去。遮罩要涵蓋 UPF 的 N6 IP。N2、N3、N6 網卡上不要預先放 172.22.6.x、172.23.6.x、172.26.6.1，否則 tester 會跳過這些 IP。

3. 核網那一邊要確認的事

在 A 上（kubectl）
# UPF 要能把 UL 送到 sink、把 DL 送到 gNB：都應該走對應的 macvlan 介面
kubectl exec -n <namespace> <upf-pod> -- ip route get 172.26.6.1
kubectl exec -n <namespace> <upf-pod> -- ip route get 172.23.6.1

# AMF 要在 N2 IP 上收 SCTP（free5GC：amfcfg.yaml 的 ngapIpList）
kubectl exec -n <namespace> <amf-pod> -- cat /free5gc/config/amfcfg.yaml | grep -A3 ngapIpList
  • tester 的 UE pool 要和 SMF 發給 UE 的範圍一樣（10.60.0.0/16）；SMF 給的 UPF N3 位址要是 172.23.49.140。
  • 訂閱資料、urrThreshold、cgf.enable 見「開始之前」。
  • A 是 VM 的話，虛擬交換器要允許一個 port 有多個 MAC（例如 VMware 的 promiscuous mode 和 forged transmits）；第 1 步 ping 得通就代表沒問題。
  • A 的 macvlan IPAM 不能發出 172.22.6.x、172.23.6.x：tester 看不到 pod 的 IP，撞到不會被擋。

Setup 頁欄位

Setup 頁的每一張卡片依序說明。「範圍／預設」的預設是 Console 第一次開啟時的值（對應 fru-lab 的 basic free5GC 範本）。欄位有問題時，錯誤訊息會直接顯示在該欄位下面。

規模（Scale）

欄位範圍／預設意思調高調低
Profile namename不可空白／basic設定檔名稱，存在 fru-lab，History 會顯示。——
gNB countscale.gnbCount≥ 1／10模擬幾個 gNB。每個 gNB 一條 SCTP、一個 N2 IP、一個 N3 IP。AMF 要處理更多 NG Setup；要更多 IP。每個 gNB 分到的 DL 變少，DL 收包分得更開。每個 gNB 的 DL 是一條連線（UPF:2152 → gNB:2152），只能由一條讀取線、一顆核心收，約 2–3 Gbps。
UE countscale.ueCount≥ 1／1000UE 總數。依序填滿 gNB，每個 gNB 容量 = ⌈UE 數 ÷ gNB 數⌉，最後一個可能沒滿。總流量 = UE 數 × 每 UE 速率。同樣總量下每個 UE 打得少，UPF 和 tester 的負載分得更平均（同一台時比較穩）；但註冊、PDU 要更久，核網裡 session 也更多。要達到同樣總量，每個 UE 得打更大。單一 UE 在 UPF 只會用一顆核心（gtp5g 約 3 Gbps 上限）。

Traffic per UE

速率都是每個 UE，不是總量；頁面下方會算出整個 run 的總 Gbps 與 pps。

欄位範圍／預設意思調高調低
Uplink / Downlink (Mbps)traffic.ulMbps / dlMbps0–10000，0 = 關／1 / 1每個 UE 每個方向的固定速率。總量變大；每個 UE 封包更密，DL 一次合得更多（省 tester CPU）。單一 UE 超過約 3 Gbps 會先卡在 UPF 的單一核心。同樣總量要更多 UE；每個 UE 封包稀疏，DL 幾乎一次送一個。
Packet sizetraffic.packetSize64 到 N3 MTU − 44（1500 MTU 時 1456）／1400內層 IP 封包長度。N3 上每個 UL 封包再多 36 bytes，DL 由 gtp5g 再多 8 bytes。成本幾乎只看「每秒幾個封包」，封包越大，同樣 CPU 打出越多 Gbps。超過 MTU 時驗證會擋下。同樣 Gbps 要更多封包，tester 和 UPF 都更吃力；適合測 UPF 處理小封包的能力。
UDP porttraffic.port1–65535／9200sink 和 UE 用的 UDP port。和主機上其他程式衝突時才需要改。
Max run timetraffic.maxDurationMin0–10080 分鐘，0 = 不限／0開始後多久自動 Stop，流程和按 Stop 一樣。長時間 run 的圖會自動壓縮，不會變慢。
Downlink batchtraffic.dlBatchMs0–10 ms，0 = 關／1每個 UE 連續送這麼多時間量的 DL 封包，讓 kernel 用一次 UDP GSO 送出（DL 的目的地是各 UE，只能合同一個 UE 的封包）。UL 不需要：同一個 gNB 的 UL 都送往 UPF，本來就會合併。一次合更多封包，tester 送 DL 更省 CPU；但每個 UE 的 DL 變得一陣一陣，同一台時容易瞬間塞滿某顆 CPU 的佇列。流量最平均，但 tester 送 DL 最吃 CPU。每 UE 10 Mbps 時 1 ms 不到一個封包，等於沒合併。

N2 setup timing 與註冊／PDU／Deregistration 步調

註冊、PDU session、Deregistration（按 Stop 後）三段各有同樣四個設定。核網快時由「每秒啟動數」決定速度；核網變慢時，「同時上限」讓請求不會一直堆上去，你會看到排隊變長。失敗但還有重試次數的 UE 會排回隊尾。

欄位範圍／預設意思調高調低
N2 setup timing
Timeout per attemptrates.n2.timeoutMs1–60000 ms／5000一個 gNB 的 SCTP 連線加 NG Setup 最多等多久。慢的 AMF 也能成功；但連不上時要等更久才失敗，Stop 也可能等更久。更快判定失敗、進入重試。
Retriesrates.n2.retries≥ 0／1失敗後再試幾次。暫時性問題可以補回來；失敗的 gNB 要更久才確定。失敗就放棄，它的 UE 記為未開始。
Registration / PDU session / Deregistration pacing（預設：50／s、200、10000 ms（Dereg 5000）、1）
Starts per secondrates.*.ratePerSec1–100000每秒最多開始幾個新的嘗試。整批 UE 建得更快，核網（AMF、AUSF、UDM、SMF）壓力更大，可能開始逾時。核網比較輕鬆，整批要更久。
Max in flightrates.*.maxInFlight1–100000同時最多幾個嘗試在等核網回應。核網慢時也能維持吞吐；但同時等的太多，逾時跟著變多。核網慢時速度跟著掉，排隊變長，但比較不會壓垮核網。
Timeout per attemptrates.*.timeoutMs1–60000 ms單一程序最多等多久。慢的核網也算成功；卡住的嘗試佔住在途名額更久。更早判定失敗、進入重試。
Retriesrates.*.retries≥ 0失敗後再試幾次，重試排回隊尾。核網明確拒絕 Dereg 時不重試。暫時性失敗補得回來，總時間變長。失敗率直接反映核網第一次的表現。

建議設定

情境規模每 UE 速率Downlink batch
第一次接新核網1 gNB × 1 UE1 / 1 Mbps1
同一台，衝高吞吐10 gNB × 1000–2000 UE15–30 Mbps1
兩台，上下行各 40G20 gNB × 800 UE50 / 50 Mbps2
  • 同一台時 UE 多、每個打少比較穩：UPF 的工作跟著 tester 發送線所在的 CPU 跑，UE 越多分得越平均；每個 UE 速率低，封包也比較平均，不容易一次塞滿某顆 CPU 的收包佇列（可再調大 sysctl -w net.core.netdev_max_backlog=10000）。實測：96 CPU、10 gNB × 1000 UE × 30 Mbps，上下行各 30 Gbps。
  • DL 要更高就加 gNB：每個 gNB 的 DL 是一條連線、一條讀取線，讓每個 gNB 的 DL 約在 2–3 Gbps 以內。
  • 兩台時：tester 那台不缺 CPU，Downlink batch 可以調到 2 ms，讓 DL 一次合更多封包。
  • 任何情況：每個 UE 單一方向不要超過約 3 Gbps（UPF 單核上限）；收 UDP 的網卡要依 port 分流（ethtool -N <網卡> rx-flow-hash udp4 sdfn）。
  • 跑的時候在 UPF 那台用 mpstat -P ALL 1 看工作有沒有分散；只有少數核心滿載，就是分流或連線數不夠。

有三張階段卡片：N2 setup（每個 gNB）、Registration（每個 UE）、PDU session（每個 UE）。按 Stop 後上面多兩張收尾卡片：UE deregistration（每個 UE）和 gNB SCTP close（每個 gNB）。五張卡片的數字意思相同：

Data plane 卡片

  • Sent／received：最近一秒的速率。received 是真正經過 UPF 回來的量，也就是 UPF 實際轉送的速率。
  • Packets per second、Total sent／received：總量算內層 IP 封包，單位是 bits（Mb、Gb）。
  • Loss：到目前為止的 1 − received ÷ sent。
  • Latency p50／p99：單向延遲，收送用同一台主機的時鐘。
  • Out of order、Send errors（本機 socket 拒絕送出的封包）。
  • Misrouted（不為 0 才顯示）：DL 從別的 UE 的隧道或別的 gNB 回來，不算收到。
  • UL 和 DL 各有一張圖，從 0 秒顯示整個 run（h:mm:ss）。虛線橘色是送出（Tx），實線綠色是收到（Rx），兩條重疊代表沒有掉包。前 10 分鐘每點 1 秒，之後每點是 2、4、8… 秒的平均。

UEs 卡片與 gNB 表

  • 依狀態計數：established、establishing、registered、registering、pending、failed、gNB down、cancelled；Stop 後加上 deregistering、deregistered。列出前 200 個失敗的 UE（SUPI、gNB、階段、原因、嘗試次數）。
  • gNB 表：每個 gNB 的 UE 註冊與 PDU 成功數、UL/DL 收到的量與掉包。
  • gNB 狀態：pending → connecting → up 或 failed。lost 表示原本 up、被 AMF 那邊斷掉，例如 AMF 重啟。

History 與 Bench

History

最近 50 個已結束的 run（fru-lab 保存）。勾兩筆可以並排比較；JSON 下載完整報告（設定與最終數字），CSV 下載吞吐時序。fru-tester 自己只保留最近 10 個，fru-lab 關著時如果結束了超過 10 個，較舊的不會進到 History。

Bench

不經過核網，量這台主機的 fru-tester 能送多快：上行封包經 loopback 送到一個不讀取的 socket，依序用 1、2、4… 條發送線到 CPU 核心數。

  • Packet size（64–9000）：改大小時 pps 幾乎不變、Gbps 等比例變，證明成本在「每個封包」。
  • Seconds per step（1–30）：每一階量幾秒，越長越穩。
  • UDP GSO：關掉就是一次一個封包（sendmmsg），可以比較前後。

Scaling 是「n 條線 ÷ (1 條線 × n)」；線越多越低是正常的，代表多出來的線在互搶。Bench 和 run 不能同時跑。

已知限制與排錯

已知限制

  • fru-tester 被 SIGKILL 時，它加的 gNB IP 會留在網卡上；之後的 run 會把它們當主機 IP 跳過，用 ip addr del 清掉。
  • NG Setup 之後 AMF 送來的訊息只讀不處理。
  • 流量在每個 PDU 建好後固定 500 ms 才開始；裝隧道比較慢的核網，每個 UE 開頭可能掉幾個 DL 封包。
  • 收尾被略過（第二次 Stop、或 fru-tester 被強制關掉）的 UE 會留在核網裡；再跑同一批 UE，free5GC 可能出現 Duplicated PDU session ID 而逾時，要重開核網。
  • 重開 free5GC 的容器時，NRF 要先重開，SMF 要在 UPF 之後；否則 SMF 失去 PFCP 關聯，每個 PDU 都會逾時。
  • gNB 後來變成 lost 時，它底下已經 established 的 UE 仍算 established。
  • UDP GRO 只在封包「合併後」才到時有用（例如實體網卡的 GRO）。Docker 的 veth 預設不做 GRO，fru-lab 的環境裡 tester 多半一次讀一個封包，結果一樣正確。
