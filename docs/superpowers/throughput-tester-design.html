01

先挑戰原始需求

原始文件的流程方向是對的：先 N2、再註冊、再 PDU、最後打流量，每一步用 channel 把 UE 往下一站送。下面這些是我認為「照字面做會出問題」或「有兩種解讀」的地方。每一張卡片都會在後面的章節給出完整設計，最後在 第 11 節 整理成需要你拍板的問題。

v3 更新
每張卡片底部的綠色「決定」是你在文件裡的回覆。第 2–10 節已照 Q1–Q17 與 N1–N7 修改，完整對照表在 第 11 節。
用 semaphore 做 rate 控管

Semaphore 控的是「同時幾個」，不是「每秒幾個」

Semaphore 限制同時進行中的程序數量。如果核網很快，每秒可能完成上千個註冊；如果核網變慢，速率會自己掉下來。兩種都不是你在設定頁輸入的「每秒 N 個」。

建議：兩個旋鈕都給。速率用 token bucket（每秒 N 個），同時進行數用 semaphore（最多 M 個 in-flight），防止核網卡住時請求無限堆積。
決定：照建議做；另外，資料面以外每個流程都有重試次數欄位（Q13）。
統計目前的 throughput 與 pps

只算送出去的量，不等於 UPF 真的轉了這麼多

Tester 自己送出 5 Gbps，不代表 UPF 有轉發 5 Gbps。如果 UPF 丟包，畫面上的數字仍然漂亮。

建議：上行在 N6 收、下行在 N3 收，送和收兩邊都計數。這樣才能算出真正的吞吐、丟包率，還能順便量單向延遲（同一台機器、同一個時鐘）。
決定：需要收包驗證（Q11）。
DL 的風暴，直接送進 N6

下行封包要能被路由到 UPF，而且要穿過 NAT

下行封包的目的 IP 是 UE IP（例如 10.60.0.12），Tester 主機必須知道「這個網段要交給 UPF N6」。另外 free5GC 的 N6 常開 MASQUERADE，上行封包離開 UPF 時來源 IP 會被改掉，無法從 IP 判斷是哪個 UE。

建議：設定頁要求填 UE IP pool 並自動檢查路由；每個測試封包的 payload 內嵌一個小標頭（UE 編號、序號、送出時間），不靠 IP 也能辨識。
決定：路由由 Tester 自動加入與移除，使用者不用處理（Q16）。
（文件沒提到）

核網裡沒有這些 UE 的訂閱資料，註冊會全部失敗

1000 個 UE 就要在 free5GC 裡有 1000 筆 subscriber，而且 IMSI、Key、OPc、DNN、S-NSSAI 要和 Tester 產生的完全一致。

建議：流程中加一個「訂閱資料準備」步驟：沿用 fru-lab 現有的 webconsole API，用同一套遞增規則批次建立，並可選擇測完後刪除。
決定：訂閱資料由使用者自己建立，Tester 不處理（Q7）。
平均分配到各個 gNB，最後一個可以不滿

「平均分配」和「最後一個不滿」是兩種不同的分法

10 個 UE、3 個 gNB：平均輪流是 4 / 3 / 3；依序填滿是 4 / 4 / 2。只有後者會出現「最後一個不滿」。

建議：預設「依序填滿」，每個 gNB 容量 = 向上取整(UE 數 ÷ gNB 數)，也可以直接指定每 gNB 上限。設定頁即時畫出分配結果（見第 6 節）。
決定：只做依序填滿，不提供選項（Q5）。
總時長 / 平均時長

「總時長」有兩種意思，而平均值會藏住慢的那一群

可以是「這一階段從第一個開始到最後一個結束的牆鐘時間」，也可以是「每個 UE 耗時加總」。另外，平均 50 ms 可能是 99% 很快、1% 卡 5 秒。

建議：兩種都顯示並清楚命名（階段耗時 / 累計耗時），另外加 p50、p95、p99、最大值。定義見第 9 節。
決定：總時長 = 第一個開始到最後一個完成（Q8）；平均與 p95 照樣顯示。
完全 copy free-ran-ue 但要拆得更細

free-ran-ue 的 UE 是「一個行程一個 UE、阻塞讀 socket」

ue.go 的註冊流程是對 TCP 連線依序 read/write；gNB 也假設每個 UE 是一條真實連線。要撐幾千個 UE，必須改成「訊息驅動」的狀態機，NAS 的編解碼與安全函式可以保留。

建議：保留 nas.go、security.go、ngapBuilder.go、TEID / NGAP ID 產生器，把流程控制重寫成第 4、5 節的形式。
直接 format 出 gtp 封包

GTP-U 標頭可能需要帶 QFI（PDU Session Container）

free-ran-ue 目前上行用 12 bytes 標頭、下一個擴充標頭類型為 0，沒有帶 QFI。部分 UPF 會要求 PDU Session Container 才能匹配 QoS 規則。

建議：封包模板支援「無擴充 / 帶 QFI」兩種，預設帶 QFI（從 PDU Session Resource Setup 的 QoS Flow 取得），對 free5GC 先實測確認。
決定：不帶 QFI，沿用 free-ran-ue 的 12 bytes 標頭（Q15）。

測試怎麼結束？

打完流量後，UE 的 PDU session、註冊狀態、SCTP 連線都還在核網裡。下一次測試用同樣的 IMSI 可能會撞到舊的 context，AMF 內的資源也不會釋放。

建議：加一個收尾階段：停流量 → PDU Release → Deregistration → 關 SCTP，同樣計數與計時；另有「立即中止」按鈕只關連線。
決定：按 Stop 後流量立即全停，再反向做 UE Dereg → gNB SCTP 斷線，每段都統計，全部停完才算結束（Q12）。原本 N5 的 PDU Release 在第 4 期實作前取消，改由核網在 Dereg 時一併釋放。可另設最長執行時間，預設無限（N6）。
02

整體架構

最大的決定是：壓測引擎要跑在哪裡。fru-lab 本身跑在 Docker container 裡，透過 Docker socket 去部署 free5GC 和 gNB / UE。打流量需要直接存取主機網卡、可能需要 raw socket 權限，還會吃滿 CPU，這些都不適合塞進 fru-lab 後端行程。

建議把引擎做成獨立的程式 fru-tester，用 host network 跑（和 fru-lab 現在部署 gNB 的方式一樣，由 fru-lab 起一個 container）。fru-lab 只負責：存設定、按開始 / 停止、把引擎推來的即時統計轉給瀏覽器、存歷史結果。

瀏覽器從不直接碰引擎。引擎只透過三張網卡和被測核網溝通：N2 走 SCTP 到 AMF，N3 走 GTP-U 到 UPF，N6 用一般 IP 從資料網路那一側送收封包。
選項做法優點缺點
A. 引擎內嵌在 fru-lab 後端同一個 Go 行程，goroutine 跑測試最快做出來，不用 IPCcontainer 網路隔離、要開特權；打流量時 fru-lab UI 會跟著卡；崩潰會一起倒
B. 獨立 fru-tester（已選定 · Q1）fru-lab 用 Docker 起一個 host-network container，透過 REST 控制、WebSocket 收統計網卡權限、CPU 綁核都只影響引擎；也可以單獨在 CLI 跑，方便自動化多一個 binary 和 API 合約要維護

fru-lab 側邊欄新增一個獨立區塊，和現有的 Dashboard / Subscriber / Logs / Images 分開，表示它是 lab 的另一個工具，不依賴 fru-lab 部署的核網。被測核網可以是任何一套，使用哪張網卡、哪個 IP 全部手動填（Q2）。

gNB 與 UE 直連（不經 Uu）

free-ran-ue 的 UE 和 gNB 之間是真的 TCP / UDP 連線，因為它們是兩個不同的行程。在 Tester 裡它們在同一個行程，所以把那條連線換成記憶體裡的信箱：

  • 上行：UE 模組產生 NAS bytes，流程模組呼叫 gNB 的「送 Initial UE Message」或「送 Uplink NAS Transport」，gNB 包進 NGAP 送到 AMF。
  • 下行：gNB 的 SCTP 讀取迴圈收到 NGAP，用 RAN UE NGAP ID 查到 UE，把 NAS 放進那個 UE 的信箱（一個小的 buffered channel）。等待中的流程從信箱取出處理。
  • gNB 自己能處理的：Initial Context Setup、PDU Session Resource Setup 這類只和 gNB 有關的訊息，gNB 直接回應，並把結果（TEID、UPF 位址）寫到 UE context，再把裡面夾帶的 NAS 轉進信箱。

好處是每個 UE 不需要自己的 goroutine 一直讀 socket。一個 gNB 只有一個讀取迴圈，UE 數量再多也不會多開連線。

左半邊是同一個行程裡的函式呼叫與 channel，右半邊才是真的網路封包。計時從 UE 送出 Registration Request 那一刻開始。

05

UE 流水線

這是你原本描述的結構，補上了速率控制、重試和失敗出口。每一站是一組 worker，站與站之間是一條 channel。一個 UE 註冊完就立刻被放進下一站，不必等其他 UE。

每條 channel 的容量設為 UE 總數，所以上一站永遠不會因為下一站慢而被卡住；「慢」只會反映在 channel 的排隊長度上，畫面會顯示出來。

速率與同時上限怎麼一起運作

每個 worker 要開始處理一個 UE 前，先拿一個 token（決定「每秒幾個」），再拿一個 semaphore 名額（決定「最多幾個同時在跑」）。UE 完成或失敗時歸還名額。失敗且還有重試次數時，UE 放回同一站隊伍的最後面重新排隊（N3）。

什麼時候開始打流量

依 Q9，UE 的 PDU 一建好就立刻加入發送，不等其他 UE。所以吞吐曲線的前段會跟著註冊與 PDU 的速率一起爬升，曲線變平的時間點大約就是最後一個 UE 進入資料面的時間。執行畫面會在圖上標出這個時間點，方便判斷哪一段才是穩定值。

整個 run 的階段

草稿→ 檢查設定、網路、CIDR→ 配置 gNB IP 與路由→ N2 建線→ 註冊 → PDU → 打流量（逐一加入，持續到按 Stop）

按下 Stop 後，順序和開始反過來：

Stop→ 流量立即全停→ PDU Release→ UE Dereg→ gNB SCTP 斷線→ 移除 IP 與路由→ 完成

PDU Release、UE Dereg、SCTP 斷線都有速率、逾時、重試與統計。按下 Stop 的當下，還在隊伍裡沒開始的 UE 直接標記為「已取消」；正在註冊或建 PDU 的，等它完成或逾時後再進入收尾；只有實際建立過的東西才需要釋放（N4）。所有 UE 與 gNB 都停完才算這個 run 結束，結束前不能開始下一個 run（Q17）。

如果設定了最長執行時間，時間到就自動觸發和 Stop 完全相同的流程；設為「無限」則只能手動 Stop（N6）。

資料面打流量

目標是用最少的 CPU 打出最多的封包，所以不開 TUN、不為每個 UE 開 goroutine。

發送

  • 分組：Active UE 平均切成 K 組（K = 可用 CPU 核心數），每組一個 goroutine 輪流替組內 UE 送封包。1 萬個 UE 也只有 K 個發送者。
  • 封包模板：UE 進入資料面時就把整個封包（GTP 標頭 + 內層 IP/UDP 標頭 + payload）預先組好，送的時候只改序號、時間戳與 checksum。
  • 控速：每組一個以 bytes 計算的 token bucket，組速率 = 組內 UE 數 × 每 UE 速率。每次批次送出多個封包（Linux sendmmsg），減少系統呼叫次數。
  • 逐一加入：UE 的 PDU 一建好就被放進目前 UE 最少的那一組（Q9），各組負載保持平均。按 Stop 時所有組立即停止發送。

測試封包 payload 標頭

每個封包的 UDP payload 前 24 bytes 是固定格式，收包端靠它辨識，不依賴 IP（避開 NAT），也能算丟包、亂序與延遲。

Q1 · 資料面的封包是怎麼產生的？

簡答：不開 TUN、不跑 UE 的協定堆疊。每個 UE 的 PDU session 建好後，tester 依核網給的參數（UE IP、UL TEID、UPF 位址）在記憶體裡組好一份封包模板；之後每送一個封包只改 24 bytes 的標頭（序號與送出時間），用一般的 UDP socket 依設定速率送出。UL 送成 GTP-U 給 UPF 的 N3，DL 送成一般 UDP 給 UE IP、由路由交給 UPF；另一端收回來後用標頭比對，算出吞吐、丟包與單向延遲。

4. 下行（DL）封包怎麼來

  1. tester 從 sink IP 送出一般 UDP 給 UE IP:9200，內容一樣是 24 bytes 標頭加填充；IP/UDP 標頭由 kernel 加。
  2. run 開始時 tester 在主機上加了一條路由「UE pool（10.60.0.0/16）經由 UPF N6 IP（10.0.1.5）」，所以這個封包會被送進 UPF。
  3. UPF 依 UE IP 找到這個 UE 的 PDU session，包成 GTP-U（TEID 是 gNB 配發的 DL TEID），送到 gNB 的 N3 IP:2152。free5GC 的 UPF（gtp5g）還會加上帶 QFI 的擴充標頭，tester 收的時候會略過。
  4. tester 在 gNB 的 N3 socket 收到後拆掉 GTP-U，讀標頭。

所以 DL 的「封包產生」在 tester，「GTP-U 封裝」在 UPF，這正好是要量的 UPF 下行轉發路徑。

5. 速率怎麼控制

  • 設定是「每個 UE 的 Mbps」。每秒封包數 = Mbps × 10⁶ ÷ (封包大小 × 8)。例：1 Mbps、1400 bytes → 每個 UE 每秒約 89.3 個封包。
  • 每條發送線用 token bucket：每 1 ms 補一次額度，最多累積 10 ms 的量，避免落後後一次爆量；有額度就輪流替它負責的 UE 送封包。
  • 發送線分配：DL 的發送線數 = CPU 核心數，UL 把同樣多條平均分給各 gNB（每個 gNB 至少一條，都從該 gNB 的 N3 IP 送出）；每條發送線有自己的 socket，UE 依編號分配到其中一條。每次系統呼叫送出最多 32 個封包（sendmmsg），減少每個封包的系統呼叫成本。
  • UE 的 PDU session 建好後等 500 ms 才開始送，讓 UPF 先裝好下行隧道；按 Stop 立即停送，再等 200 ms 收完路上的封包才結算。

7. 主管可能追問的問題

為什麼不用 TUN 介面或真的 UE 協定堆疊？
要模擬幾千個 UE，每個 UE 一個 TUN、每個封包進出 kernel 一次，成本太高，也管不動那麼多介面。要量的是 UPF 的使用者面轉發，只需要「對的封包格式、對的 TEID、對的 UE IP」，用模板直接組就夠了，也能精準控制速率。
為什麼不用 raw socket、DPDK 或 AF_XDP？
目前是 PoC 階段，一般 UDP socket 加上多 socket、批次送收，在 6 vCPU 測試機上就能收送 6.5 Gbps（掉包 0.3% 以下），瓶頸已經是 CPU，部署也最簡單（不用綁網卡、不用大頁記憶體）。更高速率的方向是先加多 socket、sendmmsg／UDP GSO，再考慮 AF_XDP（列在第 12 節「之後」與「待優化」）。
怎麼確定封包真的經過 UPF，不是在本機繞回來？
UL 送出去的是 GTP-U，只有 UPF 拆掉外層後 sink 才會收到內層的 UDP；DL 回來時是 GTP-U，而且 TEID 必須是 gNB 配發的那一個，否則記為 misrouted。DL 的路由也是明確指向 UPF 的 N6 IP。
UPF 做了 NAT，怎麼知道封包是哪個 UE 的？
不靠 IP 判斷，靠每個封包裡的 tester 標頭（UE 編號、方向、run ID）。
畫面上的 Mbps 是哪一層的？
UE 看到的 IP 層（內層 IP 封包）。N3 線路上每個封包多 36 bytes，1400 bytes 封包時線路上的量約多 2.6%。
延遲準不準？包含什麼？
收送用同一個時鐘，不會有兩台機器時間不同步的誤差。量到的是單向延遲，包含本機 kernel、Docker bridge、UPF 處理的時間。實測 1 Mbps 時 p50 約 0.05 ms、p99 約 0.1 ms。
丟包會不會其實是測試機自己丟的？
有幾個防護：每個接收 socket 開 8 MB 緩衝；送不出去的另外計數不算進 Tx；PDU 建好後延遲 500 ms 才送；Stop 後多等 200 ms 收尾。實測 1 Mbps × 4 UE 與 DL 3 Gbps 都是 0 或近乎 0 丟包。
和 iperf 有什麼不同？
iperf 需要一個真的 UE 網路介面，一次一條連線；tester 不用 UE 協定堆疊，就能讓每個 UE 都走自己的 PDU session、同時送收上下行，數字可以拆到每個 gNB，也會檢查封包有沒有走對隧道。
封包內容是什麼？支援 TCP、IPv6 嗎？
內容是 24 bytes 標頭加全 0 填充，沒有真的應用資料。目前只有 IPv4、UDP、固定速率；IPv6、TCP、突發／IMIX 流量都還沒做（列在第 12 節「之後」）。
目前的速率上限？
上限取決於機器的 CPU：發送線與接收 socket 都跟 CPU 核心數走。6 vCPU 測試機實測 UL 4.3 Gbps、DL 2.2 Gbps 同時跑（CPU 全滿，一半花在 kernel 的封包處理，包含 UPF）。單一 UE 只走一條發送線，約 1 Gbps。再往上要靠 UDP GSO 或 AF_XDP（第 12 節「待優化」）。

  3. 所有發送／讀取線共用同一組統計（程式確認）：每個封包都更新共用的計數器，延遲直方圖還有一把全域的鎖。每秒幾百萬封包、幾十顆核心時會變成排隊點。
  4. 每個 gNB 的 DL 只有一條讀取線（程式確認）：同一個 gNB 的 DL 封包來源與目的都相同，kernel 與網卡多佇列分流（RSS）都分不開，除非網卡支援依 GTP TEID 分流（例如 Intel E810）。DL 越高 gNB 要越多，40G DL 約需 20 個以上 gNB。
  5. UL 接收最多 16 個 socket（程式確認）：寫死的上限。
